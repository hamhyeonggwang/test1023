# 나의 소비생활 — 영수증 기반 소비관리 웹앱

> MVP PRD v1.0 · 2026-10-23 · 모바일 우선 / 설치 가능한 PWA

## 1. 개요

청소년 및 전환기 학생이 실제 구매 영수증을 촬영·업로드하거나 직접 입력하고, 소비를 기록·회상하며 금전관리 및 수단적 일상생활활동(IADL)을 연습하는 작업치료 지원 웹앱이다. 임상적 평가·진단 도구가 아니며 실제 소비 상황에서의 독립적 수행능력을 자동으로 판정하지 않는다.

**핵심 흐름:** 영수증 등록 → 데이터 확인 및 저장 → 소비 달력 → 필요할 때 읽기 과제 또는 구매 경험 체크 → 목표 대비 지출 확인.

## 3. 사용자 여정

1. **첫 등록**: 홈 → 영수증 등록 → 촬영/사진/직접 입력 → 이미지 및 정보 확인 → 저장 → 달력에서 확인.
2. **읽기 연습**: 홈 → 소비 연습 → 저장된 영수증 선택 → 상점·날짜·총액 문제에 터치로 답변 → 피드백 → 완료 기록.
3. **경험 체크**: 달력/영수증 상세 → 구매 경험 → 행동 4개 다중 선택 → 전체 도움 수준·느낌 선택 → 저장 또는 건너뛰기.
4. **목표**: 목표 → 예산·기간 설정 → 해당 기간 등록된 지출 합산 및 남은 금액 확인.
5. **기록 이동**: 관리 → JSON 백업 내보내기 → 다른 기기에서 파일 복원.

## 5. 데이터 모델

- `profiles`: `{id, name, createdAt}` (실명 대신 별칭 권장)
- `receipts`: `{id, profileId, date, store, amount, imageData?, createdAt, updatedAt, source}`
- `experiences`: `{receiptId, actions: string[], support: string|null, feeling: string|null, updatedAt}`
- `activities`: `{id, receiptId, profileId, answers, attempts, completedAt}`
- `goals`: `{profileId, amount, startDate, endDate, updatedAt}`
- `metadata`: 스키마 버전, 백업 생성시각, 데이터 유효성.

원화는 정수로 저장한다. 구매일과 등록일을 구별한다. 프로필·영수증·경험·활동 간 참조 무결성을 유지한다. 활동 이력과 구매 경험을 임상 점수로 자동 변환하지 않는다.

## 6. MVP 기능 우선순위

**P0:** 등록·수정·삭제, 달력, 소비 요약, 영수증 읽기 과제, 구매 경험 체크, 기간별 예산, 로컬 데이터, 백업·복원, 프로필 분리, 모바일 접근성.

**P1 (추후):** 상품별 정보 인식, 분류 드래그/터치, 가격 비교, 필요·욕구 선택, 음성 안내, 치료사용 상세 보고서 및 교육용 난이도 설정.

**범위 제외:** 은행·카드 연동, 서버 계정/자동 동기화, AI 소비 성향 진단, 결제, 자동 임상평가.

## 7. 단일 HTML 구현 사항과 제한

`index.html`은 HTML/CSS/JavaScript를 포함하는 **단일 앱 진입 파일**이다. 설치형 PWA를 위해 `manifest.webmanifest`, `sw.js`, `icons/`가 함께 필요하다. 외부 CDN과 별도 백엔드가 필요하지 않다. 브라우저 로컬 저장에 `IndexedDB`를 우선 사용한다. 파일 직접 열기(`file://`) 환경에서는 브라우저별 보안 정책으로 저장 기능이 제한될 수 있어, 그런 경우 로컬 서버나 정적 호스팅 환경에서 실행한다.

**OCR:** 정확한 한글 영수증 인식을 위한 OCR 엔진은 별도 모델/라이브러리 또는 서버 연동이 필요하다. 이 단일 파일 MVP에는 OCR을 탑재하지 않았다. 촬영·업로드한 이미지를 보며 3개 필드를 직접 확인·입력한다. OCR 결과를 제공하는 것처럼 표시하지 않는다.

**카메라:** 모바일에서 파일 입력의 `capture` 속성으로 기기 카메라를 요청한다. 브라우저/기기별 동작에 차이가 있다.

**저장·보안:** 프로필별 데이터는 앱 UI에서 분리되지만 브라우저 저장소 수준의 암호화 및 강한 사용자 인증을 제공하지 않는다. 공용 태블릿에 실명·환자식별자·결제정보가 있는 영수증 원본을 지속적으로 저장하지 않는 것이 원칙이다. 별칭을 사용하고 원본 이미지 보관 필요성을 매번 검토한다. 백업 JSON은 암호화되지 않으므로 안전하게 보관해야 한다. 공용 기기에서 민감한 자료를 사용하려면 OS별 사용자 분리나 별도 암호화/인증 구현이 필요하다.

## 8. UX 요구사항

- 모바일 세로 화면 및 태블릿 가로 화면 대응.
- 기본 조작은 터치 버튼·체크박스·선택지. 필수 드래그 없음.
- 주요 터치 영역 44 CSS px 이상 목표.
- 실제 정보 확인·과제에는 불투명한 높은 대비 카드; 글래스 효과는 홈/내비게이션 위주.
- 빈 상태, 오류 상태, 취소, 저장 피드백 및 삭제 확인 제공.
- 영수증 이미지는 등록 시 용량을 줄여 저장한다.

## 9. 인수 테스트

- [ ] 촬영·업로드·직접 입력에서 날짜·상점·금액 입력 후 저장 가능
- [ ] 수정 후 달력과 목표 합산이 갱신됨
- [ ] 소비 달력에서 다중 영수증 확인 가능

- [ ] 구매 경험을 건너뛰거나 나중에 수정 가능
- [ ] 목표 기간과 사용금액 비교가 정확함
- [ ] 별칭 프로필별 기록이 UI에서 분리됨

- [ ] 저장공간 부족·손상된 파일 등 오류가 안내됨
- [ ] 모바일에서 화면 이탈·가로 스크롤 없이 주요 기능 사용 가능

## 10. 사용성 검증 목표 (초기 제안, 임상 근거 수치 아님)

- 영수증 1장 등록 완료율 90% 이상.
- 저장 후 달력에서 다시 찾기 완료율 90% 이상.
- 테스트 시 치명적 데이터 손실 0건.
- 백업/복원 데이터 정합성 100%.
- 미인가 학생 기록 노출 0건(공용 기기 보안은 별도 강화 필요).

## 11. 실행

1. `index.html`을 Chrome, Safari 등 최신 브라우저에서 연다.
2. 저장이 제한되면 정적 호스팅(HTTPS) 또는 로컬 개발 서버에서 제공한다.
3. 별칭 프로필을 설정하고 영수증을 등록한다.
4. 기록을 옮길 때는 설정에서 JSON 백업을 내려받고 대상 기기에서 가져온다.

## 11. PWA 설치 및 배포

PWA는 **HTML 파일 하나로 배포할 수 없다.** 앱 화면과 로직은 `index.html` 하나에 유지하되, 설치와 오프라인 앱 셸 캐싱을 위해 추가 파일을 사용한다.

```text
receipt_mvp/
├─ index.html
├─ README.md
├─ manifest.webmanifest
├─ sw.js
└─ icons/
   ├─ icon-192.png
   ├─ icon-512.png
   ├─ icon-maskable-512.png
   └─ apple-touch-icon.png
```

**배포:** 전체 폴더의 파일을 동일한 경로 관계로 GitHub Pages, Vercel 또는 기타 HTTPS 정적 호스팅에 배포한다. `index.html`을 `file://`로 직접 여는 경우 설치/서비스워커는 동작하지 않는다. 로컬 테스트는 `python -m http.server 8000` 후 `http://localhost:8000`에서 수행한다.

**설치:** Android Chrome에서는 브라우저의 앱 설치/홈 화면 추가 메뉴, iOS Safari에서는 공유 메뉴의 홈 화면 추가 기능을 이용한다(기기·버전별 UI 상이).

**오프라인:** 서비스 워커가 방문 시 앱 셸(HTML, 매니페스트, 아이콘)을 캐시한다. 첫 방문과 캐시 완료 시점에는 네트워크가 필요하다. 이후 동일한 브라우저 프로필에서 재방문하면 기본 인터페이스를 오프라인에서 열 수 있다. 실제 영수증·활동 기록은 기존 IndexedDB에 저장되며, 서비스워커 캐시에 포함하지 않는다.

**업데이트:** `sw.js`의 CACHE 버전을 증가시키고 배포하면 오래된 셸 캐시를 정리한다. 데이터베이스 스키마 변경 시에는 별도 마이그레이션 정책을 수립한다.

**주의:** PWA 설치는 로컬 기록의 영구 보관 또는 기기 간 동기화를 보장하지 않는다. 앱 삭제·사이트 데이터 초기화 전에 백업 파일을 내려받아야 한다. 서비스 워커를 설치한다고 해서 공용 태블릿 프로필에 강한 접근 통제가 자동으로 생기지는 않는다.
